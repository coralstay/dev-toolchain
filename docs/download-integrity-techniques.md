# 다운로드 무결성/진위 검증 기법 (TASK-116.1)

m-11(다운로드/설치 체인 무결성 검증)을 위한 조사 산출물. 셸 기반 설치 스크립트가 원격에서
받아오는 파일(스크립트, 저장소, 패키지)의 진위·무결성을 확인하는 데 쓰이는 범용 기법을
나열하고, 각각이 실제로 무엇을 보장하고 무엇을 보장하지 않는지, 그리고 이 저장소(POSIX sh,
macOS 전용, curl/git/Homebrew/asdf만 사용)에 현실적으로 적용 가능한지 평가한다.

다음 문서(TASK-116.2)가 이 목록을 이 저장소의 실제 다운로드 지점에 매핑한다.

## 1. 체크섬 비교 (SHA-256/SHA-512)

- **보장하는 것**: 다운로드한 바이트가 체크섬이 계산된 원본 바이트와 정확히 일치함(전송 중
  손상/변조 없음).
- **보장하지 않는 것**: 그 체크섬 자체가 "진짜 게시자"가 만든 것인지는 별도로 보장하지 않음 —
  체크섬을 배포하는 채널(웹페이지, 파일)이 파일과 같은 곳에서 왔다면 둘 다 동시에 위조될 수
  있음. 체크섬은 신뢰(authenticity)가 아니라 무결성(integrity)만 담보 — 신뢰는 체크섬을
  "어디서" 받았는지(별도의, 더 신뢰할 수 있는 채널인지)에 달려 있음.
- **전제조건**: 체크섬을 다운로드물과 별도의(이상적으로는 더 신뢰도 높은) 채널로 받아야 의미가
  있음. 같은 HTTP 응답/같은 저장소에서 같이 받으면 공격자가 둘 다 동시에 바꿀 수 있어 무력화됨.
- **이 저장소에서의 구현**: `shasum -a 256 <file>` (macOS 기본 제공, 별도 설치 불필요) 또는
  `openssl dgst -sha256`으로 계산 후 스크립트에 하드코딩된 값과 `case`/`[ ]` 비교. 순수 POSIX
  sh로 구현 가능.

## 2. GPG/PGP 서명 검증 (detached signature)

- **보장하는 것**: `.asc`/`.sig` 분리 서명 파일을 게시자의 공개키로 검증하면, 그 공개키의
  개인키 보유자가 서명한 것임을 암호학적으로 보장. 커널·Node.js 릴리스가 쓰는 방식.
- **보장하지 않는 것**: 공개키 자체를 어떻게 신뢰하는지는 별도 문제(키 서버, WKD, 웹사이트에
  게시된 지문 등 — 최초 신뢰 확립(TOFU) 문제가 그대로 남음). 검증 도구(`gpg`)가 시스템에
  없으면 아예 못함.
- **전제조건**: `gpg` 바이너리 필요(Homebrew로 설치 가능하지만 이 저장소의 기본 의존성이
  아님), 게시자 공개키를 신뢰할 수 있는 방법으로 미리 확보.
- **이 저장소 적용 가능성**: 낮음 — `gpg`가 기본 macOS에 없고, 이 저장소가 검증해야 할 대상
  (Homebrew 설치 스크립트, asdf 플러그인 git 저장소)이 GPG 서명을 게시하지 않음(2026-08-30
  조사 결과, 아래 TASK-116.2 참고). 새 필수 의존성을 추가하는 비용이 이 프로젝트 규모에
  비해 큼.

## 3. minisign / signify

- **보장하는 것**: GPG와 동일한 서명 검증 목적이지만 훨씬 단순한 포맷·구현(단일 Ed25519 키,
  키 관리 인프라 불필요).
- **보장하지 않는 것**: GPG와 마찬가지로 공개키 최초 신뢰 확립은 별도 문제.
- **전제조건**: 게시자가애초에 minisign/signify로 서명을 게시해야 함.
- **이 저장소 적용 가능성**: 이 저장소가 검증하려는 업스트림(Homebrew, asdf 플러그인
  저장소들) 중 minisign/signify를 쓰는 곳이 없어 현재는 무관. 이 저장소 "자신의" 배포물
  (install.sh 자체)에 서명하는 용도로는 이론상 가능하지만, self-clone 시나리오에서는 검증
  스크립트 자체가 아직 신뢰되지 않은 상태로 막 받아진 것이라 self-signing은 순환 신뢰 문제를
  피할 수 없음(아래 SRI 항목의 한계와 동일한 구조).

## 4. Sigstore / cosign (키리스 서명)

- **보장하는 것**: OIDC 신원(예: GitHub Actions의 워크플로 identity) 기반으로 키 관리 없이
  서명·검증. 투명성 로그(Rekor)에 서명 기록이 남아 사후 감사 가능. 최근 npm 패키지, 컨테이너
  이미지 생태계에서 채택 확산 중.
  - **보장하지 않는 것**: OIDC identity 자체가 탈취되면(예: CI 파이프라인 자체가 공격당하면)
  무력화됨. 검증 도구(`cosign`)와 네트워크 접근(Rekor 조회)이 필요.
- **전제조건**: `cosign` CLI 설치, 게시자가 실제로 Sigstore로 서명해야 함.
- **이 저장소 적용 가능성**: 매우 낮음 — 이 프로젝트가 검증 대상으로 삼는 어떤 업스트림도
  Sigstore 서명을 게시하지 않고, `cosign`을 새 필수 의존성으로 추가하는 것은 "macOS 전용 개인
  툴링"이라는 프로젝트 성격에 과함.

## 5. TLS 인증서 검증/고정 (certificate pinning)

- **보장하는 것**: 전송 구간(클라이언트 ↔ 서버)이 도청/변조되지 않았음, 그리고(핀 고정 시)
  서버가 특정 인증서/공개키를 실제로 제시했음.
- **보장하지 않는 것**: **다운로드물 자체의 진위는 전혀 보장하지 않음** — 서버가 정상적으로
  TLS 핸드셰이크에 응했더라도 그 서버(또는 그 서버가 서빙하는 콘텐츠) 자체가 이미 공격자
  통제 하에 있다면(예: GitHub 저장소가 탈취됐다면) TLS는 "공격자의 콘텐츠를 안전하게
  전달"할 뿐이다. 여기가 다른 기법들과 근본적으로 다른 지점 — TLS는 전제조건(transport
  trust)이지 다운로드물 검증(content trust) 자체가 아님.
- **이 저장소에서의 구현**: `curl`은 기본적으로 시스템 CA 번들로 인증서를 검증하며(이미
  `-fsSL`로 모든 curl 호출이 이 기본 검증을 받고 있음), 별도 핀 고정은 하지 않음. 핀 고정을
  추가하면 GitHub/Homebrew의 인증서 로테이션마다 이 저장소를 갱신해야 하는 유지보수 부담이
  생기는 반면, 실질적으로 막는 위협(중간자 공격)은 이미 시스템 CA 검증으로 상당 부분
  커버됨 — 이 규모 프로젝트에서 추가 핀 고정의 비용 대비 이득이 낮다고 판단.

## 6. 코드 서명 (Authenticode / codesign / macOS notarization)

- **보장하는 것**: 플랫폼 네이티브 실행파일이 특정 개발자 인증서로 서명됐고(변조 시 서명이
  깨짐), macOS의 경우 Apple의 공증(notarization) 절차까지 통과했음.
- **보장하지 않는 것**: 셸 스크립트(`.sh`)에는 애초에 적용 대상이 아님 — 이 체계는 컴파일된
  실행파일/앱 번들 배포에 쓰는 것이라 이 저장소의 install.sh/uninstall.sh 자체나 그것이
  받아오는 텍스트 스크립트에는 구조적으로 적용할 수 없음.
- **이 저장소 적용 가능성**: 무관 — 검증 대상이 전부 셸 스크립트/git 저장소이지 macOS
  실행파일이 아님.

## 7. 패키지 매니저 자체의 신뢰 체인 (위임)

- **보장하는 것**: Homebrew bottle은 Homebrew의 CI(GitHub Actions)에서 빌드되고 GitHub
  Packages(ghcr.io)를 통해 서명된 컨테이너 이미지로 배포됨 — brew 자체가 이 체인을
  검증한다. apt/rpm의 저장소 GPG 서명도 같은 패턴(배포판 관리자에게 신뢰를 위임).
- **보장하지 않는 것**: 이 저장소가 "직접" 검증하는 게 아니라 Homebrew/asdf라는 상위
  신뢰 주체에게 위임하는 것 — Homebrew 자체가 타협되면(과거 사례 있음) 이 저장소는 그걸
  탐지할 방법이 없음. "위임"도 유효한 전략이지만, 위임하고 있다는 사실 자체를 이 저장소가
  명시적으로 인지·문서화해야 오해(이 저장소가 모든 걸 직접 검증한다는 오해)를 막을 수 있음.
- **이 저장소에서의 구현**: 이미 사실상 채택 중 — `brew install asdf`,
  `brew install $LT_BUILD_DEPS` (scripts/install/01_bootstrap_asdf.sh, 03_install_system_deps.sh)
  는 전부 Homebrew의 내부 서명/체크섬 검증에 위임하고 있고, 이 저장소는 별도 검증을 하지
  않는다. TASK-117.4(신뢰 경계 문서화)에서 이 위임 사실을 명시하는 것이 이 기법의 구체적
  적용.

## 8. git commit SHA / signed tag 고정 + `git tag -v`

- **보장하는 것**: 브랜치의 최신 HEAD(플로팅 참조) 대신 특정 커밋 SHA(불변 참조)를 지정하면,
  그 브랜치가 이후 force-push로 다른 내용을 가리키게 되어도 이 저장소가 받아오는 커밋은
  바뀌지 않음. 여기에 더해 signed tag(`git tag -s`)를 쓰고 `git tag -v`로 검증하면 그
  태그가 특정 GPG 키 보유자에 의해 서명됐다는 것까지 보장.
- **보장하지 않는 것**: 커밋 SHA 자체가 install.sh 안에 "하드코딩"돼 있으므로, install.sh를
  담고 있는 저장소/브랜치 자체가 탈취되면 그 하드코딩된 SHA도 공격자가 함께 바꿀 수 있음 —
  self-referential pinning의 근본적 한계(decision-1에서 이미 이 경계를 명시). signed tag
  검증까지 가려면 `gpg` 의존성이 추가로 필요(위 2번과 동일한 트레이드오프).
- **이 저장소에서의 구현**: `git clone --depth 1 --branch "$BRANCH"`를 커밋 SHA 고정 방식으로
  바꾸려면 `--depth 1`은 얕은 클론이 특정 SHA를 직접 가리킬 수 없는 경우가 있어(shallow
  clone은 서버가 그 SHA를 advertise해야 함 — 태그나 브랜치 tip이 아닌 임의 커밋은 일부
  git 서버에서 실패할 수 있음) 태그(예: `install-pin` 같은 안정 태그)를 고정 참조로 쓰는
  편이 `--depth 1`과 더 안전하게 호환됨. TASK-117.1에서 실제 적용.

## 9. 재현 가능한 빌드 (reproducible build) + 독립 해시 대조

- **보장하는 것**: 동일한 소스에서 동일한 빌드 결과물(바이트 단위 동일)이 나오도록 빌드
  과정을 결정적으로 만들면, 제3자가 독립적으로 같은 소스를 빌드해서 배포된 바이너리와
  해시를 대조할 수 있음 — "배포자가 준 결과물이 실제로 공개된 소스에서 나왔다"를 별도
  신뢰 없이 검증 가능.
- **보장하지 않는 것**: 소스 자체가 이미 악의적이면 무의미(소스 감사와는 별개 문제). 빌드
  파이프라인 전체(컴파일러 버전, 타임스탬프 처리 등)를 결정적으로 만드는 엔지니어링 비용이
  큼.
- **이 저장소 적용 가능성**: 무관 — 이 저장소는 아무것도 "빌드"하지 않음(셸 스크립트를
  그대로 실행/배포). asdf가 다운로드하는 언어 런타임(Node/Python/Rust/Go)의 빌드
  재현성은 각 asdf 플러그인/업스트림의 책임 영역이며 이 저장소가 관여할 수 없음
  (TASK-117.4의 "통제 밖" 범주).

## 10. SRI(Subresource Integrity) 개념의 셸 스크립트 유사 적용

- **보장하는 것**: 웹의 SRI(`<script integrity="sha384-...">`)와 같은 아이디어를 셸
  스크립트에 적용 — 원격에서 받아온 콘텐츠의 해시를 호출부 스크립트에 하드코딩해두고,
  받아온 직후 대조. "받아오는 스크립트"와 "그 해시를 검증하는 스크립트"가 물리적으로
  분리돼 있어(호출부는 이미 로컬에 있고 신뢰된 상태), 콘텐츠가 변경되면 검증이 실패함.
- **보장하지 않는 것**: 호출부 스크립트 자체가 신뢰되지 않은 채로 막 받아진 것이라면(예:
  install.sh 자신이 curl로 막 받아진 상태) 그 안에 박힌 해시도 공격자가 함께 바꿀 수 있어
  1번(체크섬) 항목과 동일한 "신뢰 채널 분리" 전제가 그대로 적용됨 — 새로운 보장을 추가하는
  게 아니라 체크섬 기법을 스크립트 안에 인라인으로 박아두는 구현 패턴에 가까움.
- **이 저장소에서의 구현**: Homebrew 설치 스크립트처럼 버전이 자주 바뀌는 대상에는 해시가
  release마다 바뀌어 유지보수 부담이 크지만(TASK-117.2에서 이 트레이드오프를 다룸), asdf
  플러그인처럼 커밋을 고정하는 경우(TASK-117.3)엔 커밋 SHA 자체가 사실상 이 패턴의 한
  형태(콘텐츠 해시 대신 콘텐츠 식별자를 고정).

## 요약: 이 저장소에 현실적으로 적용 가능한 것

| 기법 | 적용 가능성 | 이유 |
|---|---|---|
| git commit SHA/태그 고정 | 높음 | 이미 git을 쓰고 있고, 새 의존성 불필요 |
| 체크섬 비교 (SHA-256) | 조건부 | `shasum`은 macOS 기본 제공이지만, 신뢰 채널 분리가 안 되는 대상(Homebrew 설치 스크립트처럼 체크섬을 공식 게시하지 않는 경우)엔 무력 |
| 패키지 매니저 위임 (Homebrew bottle 서명) | 이미 채택 중 | brew install이 하는 일 그대로, 명시적 문서화만 추가 |
| GPG/PGP, minisign, Sigstore | 낮음 | 새 필수 의존성 추가 비용이 이 프로젝트 규모 대비 큼, 업스트림도 미게시 |
| 코드 서명/notarization | 무관 | 셸 스크립트엔 적용 대상 자체가 아님 |
| TLS 검증 | 이미 기본 적용 중 | curl -fsSL의 기본 동작, 별도 핀 고정은 비용 대비 이득 낮음 |
