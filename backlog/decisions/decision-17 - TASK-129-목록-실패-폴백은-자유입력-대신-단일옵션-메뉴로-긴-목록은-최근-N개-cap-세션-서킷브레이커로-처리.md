## Context

TASK-129는 00_select.sh의 `ask_version()`을 "default vs 자유 텍스트 입력" 2지선다에서
TASK-128이 만든 `lt_upstream_version_list()`/`lt_cached_version_list_lookup()`/
`lt_cache_version_list()` 기반 "실제 목록에서 선택"으로 교체한다. `read -r custom` 자유
입력 경로는 완전히 제거 대상이다.

decision-16은 "목록 조회 자체가 실패하면 기존 ask_version()의 'default vs 자유입력'
흐름으로 그대로 내려간다"고 적어뒀지만, 그 흐름 자체가 이번 태스크에서 제거되므로 그대로
쓸 수 없다 - 새 폴백을 이번 태스크에서 정해야 한다(decision-16도 "TASK-129에서 UI가 이
폴백을 어떻게 보여줄지 다룬다"고 위임해뒀음).

추가로 두 가지가 이 태스크 범위에서 같이 걸렸다:
1. node/java 등은 설치 가능 버전이 수십~수백 개 - `lt_arrow_menu()`는 매 키 입력마다
   전체 옵션 블록을 화면에 다시 그리는 방식이라, 옵션이 화면 높이를 넘어가면 그대로 쓰기
   어렵다.
2. TASK-129.2에 남겨진 코드리뷰 코멘트: `lt_offer_language()`가 언어를 고를 때마다
   `lt_resolve_default_version()`을 순차 호출해서, 여러 언어를 고르면 최악의 경우
   `LT_VERSION_FETCH_TIMEOUT × N`만큼 지연될 수 있다는 지적. 이번에 목록 조회
   (`lt_resolve_version_list`, 신규)가 언어당 하나씩 더 추가되므로, 그대로 두면 지연이
   최악의 경우 거의 두 배(`2 × N × timeout`)가 될 위험이 있다.

## Decision

**1) 목록 조회 실패 시 폴백: 자유 입력 대신 "옵션이 1개뿐인 동일한 메뉴"**

목록 조회(`lt_resolve_version_list`, 00_select.sh 신규)가 실패하면(오프라인, 캐시 미스 +
실시간 조회 실패, 미지원 플러그인 등) `ask_version()`은 이미 갖고 있는
`lt_resolve_default_version()`의 결과값(정적 `.tool-versions` 폴백까지 포함된 값) 단
하나만 옵션으로 담아 **같은 `lt_arrow_menu()` 위젯**을 그대로 호출한다. 자유 텍스트 입력
경로는 완전히 제거하고 대체 경로도 만들지 않는다. 실패했다는 사실은 메뉴를 그리기 직전
`tty_out`으로 한 줄 안내한다.

- 위젯을 재사용하는 이유: 옵션이 1개든 여러 개든 사용자 입장에서 "Enter로 확인"이라는
  동일한 상호작용을 유지 - 실패 시에만 별도의 안내문+수동 read 분기를 만들면 코드 경로가
  두 배로 늘고 회귀 지점도 늘어난다.
- 설치를 막지 않는다는 원칙(TASK-119.3/decision-16과 동일)은 유지된다 - 목록 조회
  실패가 곧 설치 중단은 아니고, 정적 기본값으로 계속 진행 가능하다.

**2) 긴 목록 처리: 스크롤/페이지네이션 대신 "최근 N개만 노출" cap**

`lt_upstream_version_list()`는 이미 최신순으로 정렬된 목록을 반환하는 계약이므로,
`ask_version()`은 그 목록의 **앞에서부터 최대 `LT_VERSION_MENU_MAX`(=15)개**만 메뉴
옵션으로 쓴다. 기본값(default)은 항상 메뉴 맨 위 첫 번째 옵션으로 고정 배치하고
"(default)"로 표시하며, 목록에 기본값과 같은 항목이 있으면 중복 없이 건너뛴다.

`lt_arrow_menu()` 자체(스크롤/페이지네이션 지원)는 확장하지 않는다 - 매 키 입력마다 전체
블록을 지우고 다시 그리는 현재 구조에 스크롤 상태(현재 페이지, 윈도우 오프셋)를 얹는 건
개인 툴링 규모 대비 과설계로 판단. "최근 N개"만으로 실사용에서 필요한 버전(최신 안정판
근처)은 대부분 커버되고, 그보다 오래된 patch/minor는 애초에 이 설치기로 고를 일이
드물다.

**3) 순차 네트워크 호출 지연: 목록 조회 계층에만 세션 단위 서킷브레이커 적용**

`ask_version()`이 호출하는 `lt_resolve_version_list()`는 스크립트 프로세스 전체
수명 동안 유지되는 서킷브레이커를 둔다. 어떤 플러그인에 대해서든 실시간 목록 조회가 한
번 실패하면 브레이커가 켜지고, 이후 같은 실행 안에서는(캐시 히트는 여전히 시도하되)
실시간 조회 자체를 더 시도하지 않고 곧장 실패 처리한다 - "오프라인이면 한 번만 기다리고
그 다음부터는 바로 폴백"으로 지연을 사실상 `timeout × N`에서 `timeout × 1`(목록
조회분)로 줄인다.

**구현 형태는 메모리 변수가 아니라 마커 파일이다** - 처음 구현할 때 평범한 셸 변수
(`_LT_VERSION_LIST_UNREACHABLE=true/false`)로 시도했다가, `ask_version()`이
`lt_offer_language()`에서 항상 `version="$(ask_version ...)"` 형태(값을 STDOUT으로
받으려고 커맨드 서브스티튜션 사용)로 호출된다는 걸 뒤늦게 확인하고 뒤집었다. POSIX
커맨드 서브스티튜션은 항상 서브셸에서 실행되고 그 안의 변수 대입은 호출한 쪽으로 절대
전파되지 않으므로, 언어 A를 고를 때 서브셸 안에서 플래그를 켜봐야 그 서브셸이 끝나는
순간 사라져서 언어 B를 고를 때는 다시 꺼진 상태로 시작한다 - 즉 변수 기반 서킷브레이커는
**여러 언어에 걸쳐 전혀 작동하지 않는, 조용히 아무 효과 없는 코드였다.** 파일 시스템은
서브셸 경계가 없으므로, `LT_VERSION_LIST_UNREACHABLE_FILE`이라는 마커 파일의 존재
여부(내용은 안 씀)로 대체했다 - 어느 서브셸에서 만들었든 그 다음 어떤 서브셸에서도 바로
보인다. 파일 경로는 `$$`(스크립트 전체 수명 동안 커맨드 서브스티튜션을 거쳐도 안 바뀌는
프로세스 ID)로 명명해 매번 `mktemp`를 새로 만들 필요 없이 "아직 안 트립됐으면 파일이
아예 없는" 상태를 공짜로 얻는다. 00_select.sh의 기존 EXIT trap에서 함께 정리한다.

**범위 밖으로 남기는 것**: `lt_resolve_default_version()`(TASK-119, lib.sh, 이미 테스트
통과 상태로 운영 중) 자체는 건드리지 않는다 - 이 함수 고유의 순차 호출 지연은 이번
목록-UI 교체 이전부터 있던 별개 문제이고, 여기 손대면 이미 검증된 안정 경로에 새 분기가
생겨 회귀 위험이 커진다. 따라서 완전한 오프라인 상황에서 첫 번째 언어를 고를 때는 여전히
"기본값 조회 1회 + 목록 조회 1회" 두 번의 timeout을 겪을 수 있고, 그 다음 언어부터는
목록 조회분(1회)만 서킷브레이커로 스킵된다 - 기본값 조회 자체의 timeout은 매 언어마다
여전히 발생한다. 두 계층을 하나로 합치거나 서킷브레이커를 공유시키는 건 lib.sh의 TASK-119
결과물을 변경해야 해서 이번 태스크 범위를 넘는다고 보고 보류한다. 필요해지면 별도
태스크로 분리.

## Consequences

- `ask_version()`은 이제 `(plugin, static_default_or_resolved_default)`를 받아
  내부에서 `lt_resolve_version_list(plugin)`을 호출하는 형태로 시그니처가 바뀐다 -
  기존 `ask_version(default)` 단일 인자 형태의 호출부(`lt_offer_language()` 안 2곳)도
  같이 바뀐다.
- `lt_resolve_version_list()`(캐시 조회 → 실시간 조회 → 캐시 기록, 서킷브레이커 포함)와
  옵션 목록을 만드는 순수 텍스트 로직(`lt_version_menu_options()`)은 **lib.sh**에
  추가한다(초안은 00_select.sh에 두려 했으나 옮김) - 이 저장소의 shellspec 관례상
  `Include`로 함수 단위 단위테스트가 가능한 건 lib.sh뿐이고(spec/lib_spec.sh),
  scripts/install/*.sh는 전부 최상위에서 바로 실행되는 부작용이 있어 어느 스펙도
  `Include`하지 않고 전부 서브프로세스 실행(`When run`)으로만 다룬다. 두 함수 다
  `/dev/tty`를 건드리지 않는 순수 로직이라 lib.sh로 옮기면 TTY 없이 바로
  단위테스트할 수 있고, 00_select.sh에 남겨두면 구조적으로 단위테스트가 불가능해서
  선택의 여지가 없었다. 실제 화살표 키 입력 자체(`ask_version()`이 lt_arrow_menu를
  부르는 부분)는 기존 관례(TASK-27/39/47, select_spec.sh 주석)대로 여전히
  테스트하지 않는다.
- `LT_VERSION_MENU_MAX`가 15보다 훨씬 큰 값으로 바뀌면 `lt_arrow_menu()`의 화면 전체
  재출력 방식이 다시 병목이 될 수 있음 - 그 시점이 오면 이 결정을 재검토.
