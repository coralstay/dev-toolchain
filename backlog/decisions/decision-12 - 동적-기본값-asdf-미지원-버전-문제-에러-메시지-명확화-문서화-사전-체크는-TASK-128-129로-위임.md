## Context

m-12(TASK-119, decision-4)로 `00_select.sh`의 인터랙티브 프롬프트 기본값이
`lt_resolve_default_version()`(`scripts/lib.sh:1538`) 경유로 언어 공식 소스(예: cpython
git 태그, npm registry)에서 온다. 이 함수는 캐시 → 실시간 upstream fetch → `.tool-versions`
정적값 순으로 폴백하며, upstream fetch가 성공하면 그 값을 그대로 기본값으로 제시한다.

문제: upstream(예: cpython 태그)이 새 버전을 릴리스한 시점과 asdf 플러그인(예:
`python-build`, `asdf-nodejs`)이 그 버전의 설치 정의를 따라잡는 시점 사이에는 지연이
있을 수 있다. 사용자가 프롬프트의 기본값을 그대로 수락하면, phase 5
(`scripts/install/05_install_runtimes.sh`)의 `retry 3 5 run asdf install "$plugin"
"$version"`이 "version not installable" 류의 에러로 3회 재시도 모두 실패하고, 마지막에
`die()`가 일반적인 문구("One or more runtimes failed to install: ... Re-run to retry just
the missing ones")로 종료한다. 이 문구는 일시적 네트워크 실패(TASK-88의 retry가 원래
겨냥한 케이스)를 전제로 하고 있어, "재시도해도 절대 성공할 수 없는" 버전 불일치 케이스와
구분되지 않는다 — 사용자가 재시도해봐야 똑같이 실패한다.

과거 정적 `.tool-versions` 고정값 시절에는 이 실패 유형이 존재하지 않았다 — m-12가
새로 만든 실패 표면이다.

검토한 세 옵션:

- **(a) 사전 체크**: `asdf install` 호출 전 `asdf list all <plugin>`(또는 유사)으로 그
  버전이 실제 설치 가능한지 확인. phase 5 시점엔 플러그인이 이미 설치돼 있으므로
  decision-4가 `00_select.sh`의 phase 0 기본값 제안에서 지적한 "플러그인 미설치" 제약은
  여기선 해당하지 않는다. 다만 언어별 asdf 플러그인마다 `list all` 출력 포맷이 달라
  파싱 로직이 필요하고, 그 자체가 네트워크/실행 비용이 추가되며, 이미 언어별 fetch 로직
  7종을 감당 중인 `lib.sh`에 또 다른 언어별 분기를 얹는 유지보수 비용이 든다.
- **(b) 에러 메시지 명확화**: `05_install_runtimes.sh`의 실패 경로에서 "이 버전을 asdf
  플러그인이 아직 지원하지 않을 수 있다"는 취지를 안내하고, 재시도 대신 정적 fallback
  버전이나 이전 버전 사용을 유도. 코드 변경은 `die()` 호출부 문구 수정 정도로 국소적.
- **(c) 알려진 한계로 문서화**: README에 한 줄 추가만 하고 코드는 그대로 둔다.

TASK-128(m-15, 아직 To Do, TASK-127에 의존)이 이미 "언어/동반 도구별 설치 가능 버전
전체 목록 조회"를 계획 중이고, 그 dependent인 TASK-129는 "00_select.sh 선택 UI를 실
목록 기반으로 교체, 자유 텍스트 입력 제거"를 목표로 한다. TASK-128/129가 완료되면
사용자가 애초에 asdf가 지원하는 버전만 고를 수 있게 되어, 이 문제가 UI 단계에서
구조적으로 사라진다 — 사실상 (a)를 "설치 직전 체크"가 아니라 "선택 단계의 목록 자체를
정확하게 만드는" 더 근본적인 형태로 이미 계획해 둔 셈이다.

## Decision

**(b) 에러 메시지 명확화 + (c) 알려진 한계 문서화를 함께 채택한다. (a) 사전 체크는 지금
별도로 구현하지 않는다 — TASK-128/129(m-15)가 이미 이 문제를 UI 레벨에서 근본적으로
푸는 작업으로 계획돼 있어, 지금 phase 5에 별도의 `asdf list all` 사전 체크를 추가하면
TASK-128/129 완료 시 중복/폐기될 코드가 된다.**

이유:

1. **이 저장소는 macOS 전용 개인 툴링**(README 명시, decision-4에서도 같은 전제로 java
   소스의 macOS 종속을 정당화한 바 있음)이지 범용 프로덕션 설치기가 아니다. 세션당
   1~2회 실행되는 사용 패턴에서 "아주 가끔, 최신 릴리스 직후에만" 발생할 이 희귀
   실패 유형에 상시 비용(추가 네트워크 호출 + 언어별 파싱 분기)이 드는 사전 체크를
   지금 들이는 것은 과설계에 가깝다.
2. **TASK-88의 retry는 이미 존재하지만 이 문제를 풀지 못한다** — retry는 일시적
   네트워크 실패를 겨냥한 것이고, 버전 자체가 asdf 플러그인 미지원이면 3회 재시도 모두
   똑같이 실패한다. 현재 `die()` 메시지가 "Re-run to retry"라고만 안내하는 건 이
   케이스에서 오해를 유발한다 — (b)로 최소한 이 오해를 없앤다.
3. **(a)는 이미 더 나은 형태로 계획돼 있다.** TASK-128(전체 설치 가능 버전 목록 조회)
   + TASK-129(그 목록 기반으로 선택 UI 교체)가 완료되면, 애초에 asdf가 설치 못 하는
   버전은 프롬프트에 후보로도 안 뜨게 된다 — phase 5 직전의 국소적 사전 체크보다
   구조적으로 우월한 해법이며, 이미 백로그(m-15)에 있다. 지금 (a)를 별도로 구현하면
   두 번 일하는 셈이다.
4. **(b)는 비용이 국소적이고 즉시 사용자 경험을 개선한다.** `die()` 호출부 문구만
   바꾸면 되고, 부작용이나 새로운 실패 모드가 없다.
5. **(c)는 TASK-128/129가 완료되기 전까지의 간극을 사용자에게 투명하게 알린다.**

## Consequences

- **코드 변경 필요** (이 TASK-150에서는 구현하지 않음, 별도 작업으로 명시):
  - `scripts/install/05_install_runtimes.sh`의 `die()` 호출부(파일 끝부분) 문구를
    수정 — "Re-run to retry"뿐 아니라 "일부 실패는 asdf 플러그인이 아직 해당 버전을
    지원하지 않아서일 수 있다(`asdf list all <plugin>`으로 실제 지원 버전을 확인하고
    `.tool-versions`를 수동으로 그 버전에 맞게 고쳐서 재시도)"는 취지를 덧붙인다.
    최소 변경이며 별도 shellspec 케이스(에러 메시지 문자열 검증) 추가가 자연스럽다.
  - README `🧭 알려진 한계` 섹션(`### 범위상 한계` 또는 새 소단락)에 한 항목 추가:
    "동적 기본값(m-12)이 asdf 플러그인이 아직 지원하지 않는 최신 버전을 제안할 수
    있음 — 수락 시 phase 5 설치가 실패할 수 있고, 이 경우 프롬프트에서 이전 버전을
    직접 입력하거나 재시도 시 다른 버전을 선택해야 함. TASK-128/129(m-15) 완료 시
    구조적으로 해소될 예정."
- TASK-128/129가 완료되면 이 문제 자체가 사실상 사라지므로, 그 시점에 (b)로 추가한
  에러 문구/README 항목은 재검토(단순화 또는 제거) 대상이 된다 — 지금 이 결정에
  "임시" 성격이 있음을 명시해 둔다.
- (a) 사전 체크는 TASK-128/129 완료 후에도 여전히 불필요할 가능성이 높다(선택 단계에서
  이미 걸러지므로) — 별도로 백로깅하지 않는다.
