# m-11~m-14 서브에이전트 마일스톤 실행 회고 (2026-09-03)

4개 마일스톤(m-11 다운로드/설치 체인 무결성 검증, m-12 언어 버전 기본값 자동화, m-13 Uninstall
안전성, m-14 회귀 버그 방지)을 각각 격리된 git worktree 서브에이전트로 병렬 실행해서 완료했다.
전부 로컬 `task/<ID>` 브랜치에만 커밋, push/merge 없음. 이 문서는 그 과정에서 나온 두 가지
교훈/결정을 남긴다.

## 1. 백로그 스캐폴딩을 커밋하지 않고 워크트리 에이전트를 띄우면 안 된다

`backlog task create`/`milestone add`는 마크다운 파일만 쓰고 git commit은 하지 않는다.
`isolation: worktree`로 띄운 Agent는 그 시점의 **마지막 커밋** 기준으로 새 워크트리를 체크아웃
하므로, 방금 만든(아직 커밋 안 한) 백로그 항목은 그 에이전트 눈에 아예 안 보인다.

실제로 m-14(TASK-125/126)를 `backlog task create`로 만들고 커밋하지 않은 채 곧바로 m-14 실행
에이전트를 띄웠더니, 그 에이전트는 TASK-125/126을 찾지 못하고 미션 브리핑 텍스트만 보고 자기
워크트리 안에서 TASK-125/126/m-14를 처음부터 다시 만들어서 작업했다. 완료 후 diff로 대조해보니
내용/의도는 원본과 거의 동일했지만(제목 슬러그까지 동일), `references`/`priority` 같은 메타데이터가
빠졌고, 실제 Done 처리·decision 기록은 에이전트가 재구성한 버전에만 남아 원본과 갈라지는 사고가
있었다.

**교훈**: `backlog` CLI로 마일스톤/태스크를 새로 만들면, `isolation: worktree` 에이전트를 띄우기
전에 반드시 그 변경사항을 먼저 `git commit`한다. 에이전트가 "그런 태스크를 못 찾겠다"고 보고하면
이 원인부터 의심한다.

## 2. m-11 Homebrew 설치 스크립트 SHA-256 검증 방식(TOFU) — 이걸로 충분한가 재검토

m-11 구현에서 Homebrew 설치 스크립트(`scripts/install/01_bootstrap_asdf.sh`)를 특정 커밋에
고정하고, 그 커밋 시점 내용의 SHA-256을 프로젝트가 직접 계산해 하드코딩한 뒤 매 실행마다
재검증하는 방식을 채택했다. Homebrew는 이 스크립트에 공식 체크섬/서명을 배포하지 않는다.

사용자와 함께 "이게 최선인가"를 다시 짚어봤고, 다음과 같이 결론지었다:

- 이건 TOFU(Trust On First Use) + 고정 패턴이며, SSH `known_hosts`, npm `package-lock.json`의
  `integrity` 해시, Go의 `go.sum`과 동일한 계열의 표준 대응이다 — 업스트림이 서명을 안 주는
  상황에서 실무적으로 통용되는 방법.
- 더 강한 대안(git의 content-addressing을 raw HTTP 대신 직접 활용, GPG/Sigstore 서명 검증,
  SLSA/in-toto 공급망 증명)은 각각 이유가 있어 기각했다 — 이 프로젝트 규모/성격(개인 macOS
  툴링)에 비해 과하거나, 애초에 Homebrew가 지원하지 않아 적용 불가능.
- 실제로 재검증까지 했다: 핀된 커밋(`c8188c1d48d77234a458b944d1d1b750f015a1c4`)의 실제 파일을
  다시 받아 SHA-256을 재계산해 코드의 하드코딩 값(`12479a24be3f5307eecac7cde670fad711864
  0f031229e964f544b1367b52a41`)과 정확히 일치함을 확인했다.
- 남는 한계(코드 주석에도 명시): 이 방식은 "핀 이후 내용이 몰래 바뀌는 것"은 막지만 "애초에 핀을
  뜬 시점의 원본 자체가 이미 악의적이었는가"는 증명하지 못한다. 이건 독립적인 신뢰 앵커(공식
  서명 등)가 없는 한 어떤 로컬 체크섬으로도 원천적으로 못 푸는 문제라, 설계 결함이 아니라
  스코프를 정직하게 인정한 것으로 판단하고 그대로 채택했다.

## 부록: 장시간 서브에이전트 운용 노트

m-11, m-14 에이전트는 실행 도중 세션 사용량 한도(session limit)에 걸려 중단됐다가,
`SendMessage`로 같은 agentId에 "이어서 진행하라"는 메시지를 보내 정상적으로 재개·완료됐다.
장시간 걸리는 서브에이전트를 여러 개 병렬로 돌릴 때는 이런 중단이 있을 수 있다는 걸 감안하고,
`ListAgents`/`SendMessage`로 재개할 수 있다는 점을 기억해둔다.
